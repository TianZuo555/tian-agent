# App 与后台服务一起打包，分开安装，由独立升级器协调切换

沿用 [ADR-0003](0003-keep-typescript-service.md) 的 Electron App + Node 常驻服务架构。每次发布提供一个包含 App、配套服务和升级器的 `.app`；安装后的服务独立运行，用户数据保存在稳定的数据目录。升级时由临时启动的升级器协调停止、备份、替换和启动检查，避免出现“界面更新了，后台还跑着旧代码”的情况。

## 先用一个例子说明

假设当前运行的是 **App 1.1 + 服务 1.1**，现在拿到了 **1.2 的安装包**。

用户在 App 的“服务与升级”中选择“导入新版 App…”，选中 1.2 的 `.app` 并确认。系统会暂存新版，等待当前工作空闲，退出旧 App、停止旧服务、备份数据库，再启动服务 1.2 和 App 1.2。新版界面确认自己已正常启动、配套服务版本也正确后，升级才完成，后台工作恢复。

如果新版无法启动，就恢复 App 1.1、服务 1.1 和升级前的数据库。会话、Memory、Goal、Task、Run 不需要重新创建。

**单独把新的 `.app` 拖过去覆盖，只替换了 App 文件，不会自动替换已经独立安装的后台服务。** 配套升级应通过 App 内的升级入口完成；开发调试时也可以显式安装配套服务。

## 包里有什么，装好后在哪里

开发者执行 `pnpm package`，得到 `Tian Agent.app`，包内包含：

| 内容                   | 职责                                                           |
| ---------------------- | -------------------------------------------------------------- |
| Electron App           | 显示界面，连接后台服务，提供安装和升级入口                     |
| 配套服务及 Node 运行时 | 执行 Chief、Worker、渠道接入与持久化；使用包内携带的 Node 副本 |
| 升级器                 | 在 App 退出后继续完成替换、检查和恢复；升级结束后退出          |

开发者执行 `pnpm make` 时，再由 Forge 生成分发产物；当前 macOS 配置使用 ZIP。构建所用的 Node 会被复制进服务产物，因此安装后的服务不依赖开发者的 checkout，也不依赖用户另外安装 Node。

安装后的三个位置分开管理。以下是默认路径，App 本身可以安装在其他可写目录：

```text
/Applications/Tian Agent.app
    桌面 App，以及随包携带的配套服务和升级器

~/Library/Application Support/Tian Agent/
    tian.db、pi-session.sqlite、配置及其他应用数据
    service/releases/<内容哈希>/
        已安装的服务代码及其独立 Node
    service/backups/<升级编号>/
        升级前的数据库快照
    service/app-updates/<升级编号>/
        新版 App 暂存、升级器和检查记录

~/Library/LaunchAgents/dev.tian.agent.plist
    登录自启动入口，指向已安装的服务
```

因此，App 退出后，服务仍由 macOS `launchd` 管理；App 文件被替换，也不会顺带替换或删除数据目录。不同服务版本写入不同的 release 目录，切换前保留旧目录。

## 第一次安装

1. 用户安装并打开 `.app`。
2. 在 Settings → 服务与升级中选择“安装并启动服务”。App 将配套服务与 Node 复制到数据目录，并注册当前用户的 LaunchAgent。
3. App 连接已启动的服务。之后退出 App，服务可以继续工作。

打开 App 只会按连接偏好连接现有服务，不会自动安装服务，也不会把用户主动停止的服务启动。

如果检测到没有版本信息的早期服务，先提示用户确认当前工作可以暂停，再正常停止旧进程，随后安装新版。早期服务没有任务空闲检查，不能把这次迁移描述成“保证所有任务完成后再停”。已有数据库继续复用。

## 一次配套升级的顺序

升级器必须运行在当前 `.app` 之外，否则 App 退出或自身文件被替换时，无法可靠地继续执行剩余步骤。

1. **验证并暂存。** 检查新版是否属于同一应用、App 版本是否更高、配套服务版本是否一致、平台和架构是否匹配，并校验服务所有文件的哈希。当前 App 有开发者签名时，新版必须由同一开发者签名并通过验证。确认后，将升级器和它使用的 Node 复制到独立升级目录。
2. **检查工作是否空闲。** App 先检查一次；真正切换服务时再进入维护状态、停止外部入口并检查在途请求、Durable 工作、Run 和验收操作。有活动工作时拒绝本次升级，用户稍后重试。
3. **退出并备份。** 升级器等待旧 App 退出，正常停止旧服务，在存储锁保护下备份 `tian.db`、`pi-session.sqlite`，以及存在的 WAL、SHM 文件。数据库关闭后才复制，避免复制过程中数据库仍被改写。
4. **启动新版服务，继续保持维护状态。** 切换 LaunchAgent 定义，启动新版服务，检查实际版本、release ID、数据库版本及维护状态。此时仍不恢复任务，不接受普通业务请求。
5. **替换并启动新版 App。** 在 App 所在磁盘上暂存新版，通过目录重命名切换，保留旧 App。新 App 完成界面挂载，并确认配套服务版本后，向升级器报告启动成功。
6. **提交并恢复工作。** 升级器写入成功记录，再解除维护状态、恢复服务工作，最后清理旧 App 和过早的服务产物、数据库快照。保留当前和上一版服务，以及近期数据库快照，便于诊断与恢复。

如果服务原先没有安装，App 升级只替换 App，不会顺便安装服务。如果服务原先处于停止状态，升级后仍保持停止；验证期间可以短暂启动维护实例，但不执行后台任务。

“升级配套服务”复用上述服务检查、备份和恢复流程，但不退出或替换 App。普通服务升级完成后启动服务，并让当前 App 连接它。

## 什么情况下可以回滚

**提交点是新版获准恢复业务工作的边界。** 在此之前，新版处于维护状态，升级器可以安全地恢复升级前的数据库；在此之后，新版可能已经收到新消息、创建新 Task，直接恢复旧快照会覆盖这些新数据。

| 失败发生的位置                     | 处理方式                                                               |
| ---------------------------------- | ---------------------------------------------------------------------- |
| 校验或暂存失败                     | 拒绝升级，保留原安装                                                   |
| 新服务启动或版本检查失败           | 恢复旧服务定义、数据库快照和原运行状态                                 |
| 新 App 无法启动或未通过启动确认    | 同时恢复旧 App、旧服务和数据库快照                                     |
| 升级进程在提交前异常退出           | 维护标记阻止新版自动执行工作；用户通过“恢复未完成升级”按日志恢复       |
| 已提交，但恢复工作或清理旧文件失败 | 保留新版和当前数据；重试激活，清理失败留待后续处理，不自动恢复旧数据库 |

这是可恢复的多步流程。升级日志和维护标记保存在数据目录，进程退出后仍可读取。它不提供零停机升级，也不承诺整个 App 目录与所有数据库在断电时作为一个整体原子提交。

数据库备份只覆盖应用管理的两份 SQLite 及其辅助文件，不会回滚用户项目里的代码、外部文件或已经发生的远端操作。未来若要迁移其他文件格式，必须为那些文件单独设计备份与恢复。

## 退出、断开、停止、自启动的区别

| 用户操作       | 后台服务                         | 下次打开 App                           |
| -------------- | -------------------------------- | -------------------------------------- |
| 退出 App       | 继续运行                         | 按保存的连接偏好连接服务               |
| 断开本窗口连接 | 继续运行，后台工作不受此操作影响 | 保持不自动连接，直到用户重新连接       |
| 停止服务       | 正常退出，所有渠道暂时不可用     | 不会自动启动服务，需要手动启动         |
| 关闭登录自启动 | 当前运行的服务继续运行           | 不影响连接偏好；下次登录不自动启动服务 |

登录自启动、服务是否正在运行、App 是否连接，是三个独立状态。App 升级保留这些选择；用户显式执行“安装／升级配套服务”则会启动服务并连接当前 App。

## 选择这个方案的原因与边界

- **服务独立安装**：App 可以退出或被替换，长期工作仍有独立生命周期。代价是需要显式管理 App 与服务的版本配对。
- **配套打包**：用户只需要取得一个 `.app`，里面有对应的服务和运行时。代价是安装包更大，但服务不会因为系统 Node 被删除或更新而无法启动。
- **独立升级器与维护窗口**：允许短暂停机，换取单个写入者、可检查的切换和提交前恢复。无需让两个服务同时写同一份数据。
- **当前使用本地安装包**：已实现导入新版 `.app`，尚未配置远端版本检查、下载源、自动发布签名与公证流程。校验哈希和已有签名不等于已经建立自动更新发布渠道。
- **兼容性明确拒绝**：当前升级器只接受它支持的协议与数据库版本。未来引入破坏性变化时，必须同步扩展迁移和升级器；不能假设保留旧文件就支持任意版本间升级或降级。
- **当前目标是本机 macOS**：服务管理依赖 `launchd`；其他平台需另行实现服务生命周期与安装机制。
